## 1. 범위와 변경 경계

- 번호는 [통합 시연안 #123](https://github.com/neuroplan-hybrid/neuroplan-aws-migration/pull/123)의 **T4 RDS PITR**을 따른다. 이전 번호 T4(VPN, 현 T5)와 구분한다.
- 원본: `neuroplan-rds-operation` / 리전 `ap-northeast-2` / MariaDB.
- 복원본: `neuroplan-rds-pitr-20261016`. 전날 계획의 20261015 이름은 실제 생성 전에 변경했다.
- PITR은 **기존 원본을 덮어쓰거나 삭제하는 방식이 아니라, 지정 시점으로 복원된 새 DB 인스턴스를 생성**하는 방식으로 실행했다. 최신 수동 스냅샷 선택 복원과 구분한다.
- 원본 데이터 삭제/변경, 애플리케이션 DB 연결 변경, DNS 전환, 원본 deletion protection 변경은 이 T4 절차에 포함하지 않았다. 원본 deletion protection 조회값은 false였으며 이를 켜지 않았다.
- 복원본은 **Single-AZ / 비공개 / db.t4g.micro**, 원본과 같은 DB 서브넷 그룹·보안 그룹·DB 파라미터 그룹·옵션 그룹을 사용하도록 요청했다. 실제 상태 조회에서도 동일 서브넷 그룹·SG, 비공개·Single-AZ를 확인했다. 관리용 식별자 전체는 이 문서에서 생략한다.
- 원본은 `ap-northeast-2a` / Multi-AZ=true, 복원본은 `ap-northeast-2c` / Multi-AZ=false로 관측됐다. 서로 다른 AZ라는 사실만으로 데이터 정합성을 판단하지 않는다.
- 기존 AWS CLI와 MariaDB 클라이언트를 호출하는 로컬 작업용 스크립트를 DevOps VM에서 수동 실행했다. 전용 exporter/상시 SQL 수집 서비스 설치나 네트워크 변경은 하지 않았다. RDS의 내부 Enhanced Monitoring 구성 상태 전이는 별도 관측 사항이다.
- 이 PR은 **실측 결과 문서 1개만 추가**한다. 실행 스크립트·Terraform·GitOps·모니터링 설정은 포함하지 않으며, PR 작성 과정에서 AWS/DB 변경을 수행하지 않았다.

## 5. SQL 행 수 비교

- 범위: `infraready` 스키마의 **모든 BASE TABLE**에 대한 실제 `COUNT(*)` 합계. `information_schema.TABLE_ROWS` 추정치를 사용하지 않았다.
- 각 DB의 합계는 여러 COUNT를 하나의 UNION SELECT로 묶어 조회했다. InnoDB는 해당 statement의 읽기 시점 기준이며, 원본과 복원본은 **순차 조회**다. 전체 두 DB에 걸친 동시 스냅샷이 아니다.
- 원본과 복원본의 테이블 이름 목록에서 생성한 scope 해시가 같았다. **scope는 테이블 목록 해시이지 행 내용 체크섬이 아니다.**
- 복원본에 자체 MasterUserSecret이 없어 기본 명령은 중단했다. 이후 실행자가 명시적으로 `--allow-source-secret`을 선택해 원본의 현재 인증 정보를 사용했으며, **SQL 접속 대상은 복원본의 별도 Endpoint**다. 비밀번호를 변경하지 않았다. 이 방식의 성공은 이번 시점의 인증 정보가 유효했다는 결과이지 모든 과거 복원에 유효하다는 보장이 아니다.
- TLS CA 및 서버 인증서 검증을 켠 기존 MariaDB 클라이언트로 SELECT를 실행했다. 자격 증명과 Endpoint 원문은 이 PR에 포함하지 않는다.

| 대상 | 총 행 수 | 조회 완료 |
| --- | --- | --- |
| 원본 neuroplan-rds-operation | **5,418** | 10:20:38 |
| 복원본 neuroplan-rds-pitr-20261016 | **5,418** | 10:20:39 |

**비율 = 복원본 행 수 / 비교 시점 원본 행 수 × 100 = 100.00%.** 사전 09:58:25의 5,418을 분모로 고정한 것이 아니라 최종 비교 시 원본을 다시 조회했다. 10:00:02 시점의 별도 정확한 기준 행 수는 확보하지 않았다.

행 수는 사용자 수/업무 건수가 아니며, 테이블 간 관계 중복을 제거하지 않는다. 동일 행 수에서도 수정된 값·삭제 후 삽입 등 내용 차이가 있을 수 있다. 이번 시험에서는 원본 데이터를 의도적으로 삭제하지 않았으며, 변경 전후 특정 행의 상태 복원·전체 내용 체크섬은 최종 검증 범위에 포함하지 않았다.
